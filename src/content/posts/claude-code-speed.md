用了几个月 Claude Code 之后，我有一个越来越强的直觉：**晚上的响应速度比白天快很多。**

不是那种微妙的"好像快了一点"，而是体感明显——白天经常卡住等半天，晚上基本秒回。

直觉不可靠，数据可靠。于是我让 Claude Code 分析了自己的速度。

## 数据

Claude Code 的所有会话记录以 JSONL 格式存储在本地 `~/.claude/projects/` 下。每条消息都带有精确时间戳和 token 用量。

- **384 个 session**
- **23,498 个有效数据点**（user → assistant 的响应对）
- 时间跨度覆盖近两个月的日常使用

"响应时间"的定义：user 消息的 timestamp 到紧邻的 assistant 消息的 timestamp。经过验证（下文会讲），这个 timestamp 是**回复完成时间**，不是首 token 时间，即包含了排队 + 推理 + 全部 token 生成的端到端耗时。

## 结论先行

| 时段（北京时间） | 中位响应时间 | P90 | 样本数 |
|---|---|---|---|
| 🌙 深夜 22:00-06:00 | 6.0s | 18.7s | 5,503 |
| ☀️ 白天 08:00-20:00 | 8.8s | 42.5s | 15,539 |
| 🌆 傍晚 20:00-22:00 | 9.0s | 48.9s | 2,036 |

**深夜比白天中位数快 32%，P90 快 2.3 倍。统计检验 p < 0.0001。**

## 为什么

**北京 14:00-17:00** ≈ 美东上午工作时段。美国开发者上班开始用 Claude，API 负载飙升。P90 到 44-55s。

**北京 19:00-20:00** ≈ 美东上午黄金时段。P90 最高达 **57.8s**——10% 的请求要等将近一分钟。

**北京 02:00-05:00** ≈ 北美深夜，美国人睡了。中位数 4.8-5.9s，P90 也才 13-16s。

Anthropic 的推理集群大概率主要部署在北美。中国深夜 = 北美非高峰 = 排队少 = 快。就这么简单。

## 不只是"回复短"

一个合理的质疑：也许深夜我做的任务比较简单，回复更短，所以看起来快？

按 output tokens 归一化后：

| 时段 | 归一化响应时间 (s/1k tokens) |
|---|---|
| 🌙 深夜 | 38.1 |
| ☀️ 白天 | 44.2 |

排除了回复长度差异后，**仍然快 14%**。API 侧确实更快，不是幸存者偏差。

这 14% 大概率来自两个因素叠加：排队时间更短，以及高峰期 GPU 被更多请求共享、每个请求分到的算力更少导致生成速度本身也下降。

## P90 才是真正的体感

中位数快 32% 听起来还行。**但 P90 才是你的真实体感。**

白天，10% 的请求要等 42-58 秒。每做十轮交互，就有一次让你盯着屏幕等快一分钟。这一分钟足够你切到微信、刷一下朋友圈、忘记自己刚才在想什么。心流断了。

深夜，P90 也才 18.7 秒。几乎不会遇到"卡住"的情况。心流不断。

这就是为什么体感差距比数字显示的更大——人对"偶尔卡一次"的记忆远比"平均快一点"深刻。

## 方法论彩蛋：timestamp 到底是什么

分析过程中遇到一个关键问题：JSONL 里 assistant 消息的 timestamp 到底是**首 token 时间（TTFT）**还是**回复完成时间**？

如果是 TTFT，diff ≈ 排队延迟 + prefill，应该跟回复长度无关。
如果是完成时间，diff = TTFT + 全部生成时间，跟回复长度强相关。

验证方法：看响应时间和 output tokens 的关系。

| Output Tokens | 中位耗时 | 隐含 TPS |
|---|---|---|
| 200-500 | 10.5s | 28.5 |
| 500-1000 | 16.4s | 38.6 |
| 1000-2000 | 22.9s | 55.1 |
| 2000-4000 | 51.1s | 64.6 |
| 4000-10000 | 95.9s | 58.1 |

强线性关系 → **timestamp 是回复完成时间**，确认。

隐含 TPS 随 token 数增大趋近 ~60，这是 Opus 4.6 的稳态生成速度。短回复的 TPS 低（28），是因为 TTFT 的固定开销被短回复放大了。反推：稳态 60 TPS，350 tokens 纯生成约 5.8s，10.5s 总耗时减掉 5.8s，**TTFT ≈ 4.7s**。跟 Opus 级模型的 prefill 延迟大致吻合。

## 最近两周差距在扩大

| 时段 | 全量中位数 | 近两周中位数 |
|---|---|---|
| 🌙 深夜 | 6.0s | 6.4s |
| ☀️ 白天 | 8.8s | 10.6s |
| **差距** | **32%** | **39.2%** |

白天在变慢，深夜基本没变。可能原因：Claude Code 用户在快速增长，白天 API 负载越来越重，Anthropic 的推理容量没有同步跟上。

## 实际建议

如果你在东八区重度使用 Claude Code：

1. **密集 coding session 放到 22:00 以后**——架构设计、大范围重构、需要多轮快速交互的任务
2. **白天做对延迟不敏感的事**——code review、写文档、单次长 prompt
3. **避开 14:00-17:00 和 19:00-20:00**——P90 接近一分钟的地狱时段

当然，最好的建议是：Anthropic 加机器。
